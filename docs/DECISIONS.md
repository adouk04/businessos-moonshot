# BusinessOS: Architecture Decision Records

Format: **Context → Decision → Consequences.** Add new ADRs at the bottom; never rewrite history, supersede instead.

## ADR-001: Modular monolith on Next.js + Supabase
**Context:** Solo developer, ~3 weeks to demo, long-term product ambitions.
**Decision:** One Next.js app, one Supabase project. Logical modules (`domain/`, `server/`, `components/`), no separate services.
**Consequences:** Fastest path; simple deploy. Boundaries are enforced by convention and folder rules, so keep `domain/` free of framework imports so it can be extracted later.

## ADR-002: Business logic in pure functions under `src/domain`
**Context:** Revenue math, opportunity detection, and simulation must be correct and independently testable; AI must never invent calculations.
**Decision:** All calculations are pure TypeScript functions with no I/O. Components and actions call them.
**Consequences:** Fast, deterministic unit tests. Slightly more plumbing (fetch rows, then compute).

## ADR-003: Authorization = server-derived business context + RLS
**Context:** The spec requires business-level isolation and never trusting client-provided IDs.
**Decision:** `requireBusiness()` derives the business from the session and `business_members`. RLS policies using `is_business_member()` are enabled on every tenant table, and server code uses the user-scoped client so RLS applies. `proxy.ts` is only an optimistic redirect.
**Consequences:** Two independent layers must both fail for a leak. RLS adds a membership lookup per query (indexed, negligible at this scale). Tests need a real Postgres.

## ADR-004: Money as integer cents (`bigint`)
**Context:** Floating point causes rounding errors in financial totals.
**Decision:** Store and compute cents as integers. Parse user input from strings (no `parseFloat`). Format only at the UI edge. Percentages applied once, with explicit rounding (half up), at the end of a calculation.
**Consequences:** Needs care with divisions; JS numbers are safe to 2^53 cents (~$90 trillion), which is ample. Implemented in `src/lib/money.ts` with tests.

## ADR-005: Composite foreign keys for tenant integrity
**Context:** A buggy query could attach a customer from business A to an appointment in business B.
**Decision:** Parents expose `unique (id, business_id)`; children reference `(parent_id, business_id)`.
**Consequences:** Cross-tenant links are impossible at the DB level. Slightly more verbose schema.

## ADR-006: Completion does not imply payment; one sale per appointment
**Context:** Spec: completed ≠ paid; completing twice must not duplicate sales.
**Decision:** Status changes never write transactions. Sales are recorded explicitly. A partial unique index enforces at most one sale per appointment.
**Consequences:** The owner has one extra step but books stay honest. Split payments/deposits aren't supported until the index is relaxed (post-MVP, documented).

## ADR-007: Compute derived data on demand (no stored opportunities/metrics)
**Context:** Small data volumes; stale derived rows are a correctness risk.
**Decision:** Dashboard metrics, opportunities, and simulations are computed from source rows when requested.
**Consequences:** Always consistent; revisit with SQL aggregates if performance demands, keeping function signatures.

## ADR-008: Tooling choices and versions (2026-11-15)
**Context:** Scaffold generated by current `create-next-app` and `shadcn` CLIs.
**Decision / facts recorded:**
- Next.js **16.4** + React **19.3**, Tailwind **4**, Turbopack. `middleware` is now **`proxy.ts`**. The generated `AGENTS.md` instructs agents to read `node_modules/next/dist/docs/` because APIs differ from older knowledge. Do so before writing Next-specific code.
- The scaffold enables `cacheComponents` and `partialPrefetching` in `next.config.ts`. Consequence for Phase 1: any runtime data access (cookies, headers, DB) must happen inside a `<Suspense>` boundary or dynamic-aware component. Plan the auth shell accordingly; if this causes friction, disabling `cacheComponents` is an acceptable, documented fallback.
- shadcn/ui now generates components on **Base UI** (not Radix): triggers use the `render` prop instead of `asChild`. It also generates `import { cn } from "cn"`, a package maintained by the shadcn team (github.com/shadcn-ui/cn) replacing clsx + tailwind-merge.
- Vitest **5**, Playwright. `@types/node` pinned to ^24 (Vitest peer requirement).
- `npm audit` reports moderate advisories (deepmerge, minimatch) only in the `shadcn` CLI's dependency tree; no non-breaking fix exists. Not in the runtime request path; revisit when upstream patches.
- Test runner config is `vitest.config.mts` (ESM) to avoid a Vite config-loader warning.
**Consequences:** Newer, less-documented territory; follow the bundled docs and record surprises in DEVLOG.

## Resolved decisions (2026-11-15, owner)
1. **RLS test environment:** hosted Supabase project (owner creates it and provides keys); no Docker. Integration tests create and delete throwaway users with the service-role key, which is used **only** in tests and e2e teardown, never in the app. Consequence: tests write to the real dev project, so they only touch accounts named `rls-*` / `e2e-*@example.test` and clean up after themselves.
2. **Email confirmation:** OFF for the demo project (Supabase Auth settings). The sign-up action still handles the confirmation-required case. Turn it back on before any real launch.
3. **Cloud projects:** free-tier Supabase and Vercel projects are approved. The owner creates the Supabase project; deployment to Vercel is still confirmed with the owner at release time.

## ADR-010: Phase 1 auth design (2026-11-15)
- `@supabase/ssr` cookie sessions. `src/proxy.ts` refreshes the session with `getClaims()` and does optimistic redirects only.
- `getUser()` in `src/server/auth/session.ts` verifies with the Auth server; `requireBusiness()` resolves the business from `business_members` and is called by the `(app)` layout. Pages that run queries must also call it themselves (layouts do not re-run on every navigation).
- Under `cacheComponents`, session reads sit behind `<Suspense>` (layout `Gate`, onboarding `Gate`).
- Sign-in returns one generic error for wrong password or unknown email. Sign-up maps known error codes to friendly messages and logs only the error code.
- Onboarding uses the `create_business()` security-definer RPC, so business and owner membership are created atomically; direct inserts into `businesses` / `business_members` are denied by RLS.
